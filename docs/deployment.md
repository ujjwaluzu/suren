# Cloudflare deployment

## Compatibility and build approach

The implementation selects **Next.js 16.4.3**, **React 19.3.1**, **OpenNext Cloudflare 1.20.14**, and **Wrangler 4.156.0**, pinned in the package and lockfile. The installed adapter declares support for Next `>=15.5.28 <16 || >=16.4.1`. The [OpenNext compatibility guide](https://opennext.js.org/cloudflare) and [installation guide](https://opennext.js.org/cloudflare/get-started) were reviewed during implementation. Cloudflare also documents the [OpenNext adapter](https://developers.cloudflare.com/workers/framework-guides/web-apps/opennext/).

Use the Next **Node runtime**, not `runtime = 'edge'` and not the old `next-on-pages` adapter. The configuration includes `nodejs_compat`, public fetch compatibility, the ASSETS binding, self-reference service, and an enquiry rate-limit binding. The code does not use ISR or runtime image transformations, so an R2 cache and paid image binding are not required for this content model. Static pages are regenerated by rebuilding. Media is pre-optimised WebP and SVG; `next/image` supplies dimensions and lazy loading without a transformation service.

Use Linux CI or WSL for the most predictable adapter builds; Windows support has adapter-specific limitations. A normal Next production build is a separate check from an OpenNext Worker build. Do not treat either as proof of deployment.

## 1. Complete identity and configuration

Set real operator details in `src/config/brand.ts`, verify the intended name/domain independently and review privacy/terms for the actual operating jurisdiction, data regions and retention. The current legal pages deliberately expose a pre-launch notice while operator identity is empty.

The planned domain is `surencompany.com`, to be purchased later. Once purchased and configured, set `NEXT_PUBLIC_SITE_URL=https://surencompany.com` during build **and** runtime. Keep `http://localhost:3000` for local development until then. Public variables are compiled into the browser/static pages; changing a runtime secret cannot update static canonical URLs. Leave optional social and public contact details empty until verified.

## 2. Prepare PostgreSQL

Create or select the intended Supabase project. Apply `migrations/001_enquiries.sql` through the Supabase SQL editor or your normal migration runner. Apply exactly once to a new schema; later changes should be separate forward migrations.

The migration creates `leads`, `lead_deliveries` and `enquiry_rate_limits`. It enables RLS on all three and gives no table privileges or read policies to `anon` or `authenticated`. Only the backend uses the service role. Rate-limit and delivery-claim functions revoke public execution and grant it to `service_role`. The lead insert trigger creates the outbox in the same transaction.

Verify that anonymous REST requests cannot read, insert, update or delete records, and cannot call the privileged RPCs. The embedded PostgreSQL tests validate the migration mechanics, not your account's broader settings. Review who can access Supabase backups and the dashboard.

## 3. Prepare email and optional services

Verify your sender domain in Resend and use a sender on it for `RESEND_FROM_EMAIL`. Set the actual founder recipient. Check provider restrictions and send to both a controlled client address and the founder address in staging. An API key alone does not prove DNS verification or successful delivery.

If HubSpot is required, provision a private app token with the minimum contact scopes needed for contact upsert and verify it in a non-production pipeline/account first. Omit the token to mark CRM tasks skipped. Optional GA requires a real measurement ID; optional Sentry requires a real DSN. No telemetry service is active without configuration.

## 4. Configure Cloudflare

Authenticate your local Wrangler CLI or configure your CI using Cloudflare's supported account/token mechanism. Do not commit credentials. Set an account-unique Worker name in `wrangler.jsonc`, updating the self-reference service to match. The rate-limit namespace ID is an account-local identifier; change `1001` if it conflicts with another limiter you manage.

Use Wrangler secrets for server credentials:

```text
npx wrangler secret put SUPABASE_SERVICE_ROLE_KEY
npx wrangler secret put RATE_LIMIT_SALT
npx wrangler secret put RESEND_API_KEY
npx wrangler secret put RESEND_FROM_EMAIL
npx wrangler secret put CONTACT_NOTIFICATION_EMAIL
# Optional:
npx wrangler secret put HUBSPOT_ACCESS_TOKEN
npx wrangler secret put SENTRY_DSN
```

Set the public site URL and Supabase URL as normal environment variables at build/runtime. Explicitly remove `ENQUIRY_MODE=local` for a hosted deployment. `.env.local` is for Next development; use an ignored `.dev.vars` for Workers preview secrets as appropriate to Wrangler. Use a dedicated staging database and controlled recipients when testing live integrations. Never reuse a production recipient list for automated E2E tests.

## 5. Build, preview and deploy

```text
npm ci
npm run typecheck
npm run lint
npm test
npm run build:cloudflare
# Preview the generated Worker:
npx opennextjs-cloudflare preview
# Deploy after successful staging checks:
npx opennextjs-cloudflare deploy
```

`npm run deploy` combines build and deploy. No deployment was performed during implementation. Connect your owned domain through Cloudflare after the Worker exists. Ensure HTTPS and check `/robots.txt`, `/sitemap.xml`, canonical tags, social previews and headers at the real hostname. A localhost build disallows indexing until rebuilt with a configured public URL.

Favicon checks: the homepage must include icon links, and `/favicon.ico`, `/favicon.svg`, `/favicon-96x96.png` and `/apple-touch-icon.png` must return HTTP 200 with image content types and no authentication or `X-Robots-Tag: noindex` header. The public `robots.txt` allows the homepage and these files, including for Googlebot and Googlebot-Image. Preserve these stable URLs. Local development deliberately disallows crawling; rebuild with the production `NEXT_PUBLIC_SITE_URL` to enable public crawling. Search engines choose when to refresh and display the favicon after recrawling the homepage.

In staging, submit a controlled enquiry and inspect: one lead, three outbox records, client receipt, founder notification and a CRM result if configured. Confirm invalid requests fail, failed notifications remain retryable, private records remain private, and rate limits work in Workers. Production live mode expects the Cloudflare-provided `cf-connecting-ip`; it does not trust IP headers in a plain Node preview.

## 6. Release and rollback

Record the deployed Worker version and the source revision in your release log. Retain a known-good version in Cloudflare. For rollback, use the dashboard's Worker version rollback or `npx wrangler rollback <version-id>` after checking `npx wrangler deployments list`. Verify the public pages and controlled enquiry again.

Code rollback does not roll back the database. The initial migration is additive. Preserve the lead/outbox schema while reverting application code; export a backup and use a reviewed forward correction for data/schema problems. Never drop the lead tables as a routine rollback.

Assign an operator to delivery retries, backlog alerts, backups/restores, dependency updates and retention before collecting live leads. See operations documentation.
